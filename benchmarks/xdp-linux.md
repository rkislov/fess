# Linux: HTTP RPS с XDP и без него

## Результаты 21 октября 2026

Две успешные Linux-серии, 60 прогонов, 7 599 972 измеренных HTTP-запроса и
28 798 462 синтетических пакета. Транспортных ошибок, неожиданных HTTP-кодов
и расхождений access-журналов нет. Фактическая нагрузка близка к 50 000 PPS.
JSON: `xdp-linux-generic-2026-10-21.json` и `xdp-linux-native-2026-10-21.json`.

Native/veth: AMD EPYC 9V45, 4 vCPU, Linux 7.0.0-1017-azure. Медианы трёх
повторений, успешный RPS с учётом сброса журнала, XDP off → on:

- Без атаки: 15 086 → 15 072 RPS (−0,09%; диапазоны повторений перекрываются).
- SYN, CIDR deny: 12 394 → 14 695 RPS (+18,57%); p95 2,88 → 2,44 мс.
- SYN, rate limit: 12 789 → 14 299 RPS (+11,81%).
- UDP, CIDR deny: 13 996 → 14 363 RPS (+2,62%).
- UDP, rate limit: 14 292 → 14 782 RPS (+3,43%).

Generic/veth: AMD EPYC 7763, 4 vCPU, тот же Linux. Медианы off → on:

- Без атаки: 7 693 → 7 695 RPS (+0,03%; диапазоны перекрываются).
- SYN, CIDR deny: 6 218 → 7 208 RPS (+15,93%); p95 5,37 → 4,47 мс.
- SYN, rate limit: 6 236 → 7 082 RPS (+13,56%).
- UDP, CIDR deny: 6 983 → 7 229 RPS (+3,51%).
- UDP, rate limit: 6 914 → 7 054 RPS (+2,02%).

CIDR-сценарии отбросили ровно 100% отправленных атакующих пакетов, не затронув
HTTP-клиента. SYN rate limit отбросил около 97,83%; через фильтр прошло по
13 000 SYN за каждый 12-секундный прогон (пересечение 13 фиксированных окон).
UDP rate limit отбросил около 78–80%; лимит не должен давать 100% отбрасывания.
SYN cookies без XDP: около 1,57 млн за три повторения каждого SYN-сценария;
с CIDR deny: 0. С SYN rate limit cookies остаются: лимит пропускает часть SYN
и не является SYN proxy. Для generic доля softirq CPU в CIDR SYN-сценарии
снизилась с 22,4% до 8,3%, для native — с 15,0% до 6,8% (медианы).

Вывод: на этом стенде XDP сохраняет HTTP-производительность под SYN-нагрузкой
и снимает обработку запрещённых пакетов с TCP/IP-стека. Без атаки измеримого
ускорения HTTP нет. Небольшой выигрыш UDP RPS сопоставим с разбросом повторений,
поэтому его нельзя считать устойчивым приростом, хотя packet-drop доказан
счётчиками. Native и generic выполнялись на **разных CPU**, их абсолютный RPS
нельзя использовать для сравнения эффективности режимов. Физическая NIC,
предел PPS, распределённый flood, TLS и production-политики здесь не измерены.

## Повторение и методика

Стенд запускается через `.github/workflows/xdp-benchmark.yml` вручную:

```sh
gh workflow run xdp-benchmark.yml --repo rkislov/fess -f mode=generic
gh workflow run xdp-benchmark.yml --repo rkislov/fess -f mode=native
```

Для самостоятельного запуска нужны Linux 5.15+, root, Go, clang с BPF target,
iproute2 и iptables. Соберите `dist/fess`, `dist/fess-xdp`, `dist/fess-load`,
`dist/fess-rawload` (из `./benchmarks/rawload`) и `dist/fess-xdpstats`
(из `./benchmarks/xdpstats`), затем выполните:

```sh
sudo python3 benchmarks/xdp-linux.py --mode generic --seconds 12 --repeats 3 \
  --pps 50000 --output benchmarks/xdp-linux-results.json
```

Скрипт создаёт временные veth и network namespace без default route, а затем
удаляет их. Генератор использует только тестовые IPv4-адреса 192.0.2.0/24 и порт
18080. Он не подключает XDP к физическим интерфейсам. На выделенном стенде порты
18080–18082 должны быть свободны. Локальная панель тестового FESS работает без
аутентификации только на 127.0.0.1; временная БД удаляется после прогона.

В каждом режиме выполняются 30 прогонов: пять сценариев, XDP off/on, три
повторения. Во втором повторении порядок on/off обратный. В каждом прогоне новая
SQLite, один неблокирующий WAF rule, пакетное журналирование, upstream с ответом
9 байт. ClamAV, ICAP, HTTP rate limit и bot protection отключены. HTTP: 16
параллельных клиентов, 1 секунда прогрева и 12 секунд измерения. Новый HTTP-клиент
создаёт соединения при начале измерения; затем использует keep-alive.

Сценарии: обычный HTTP; HTTP + SYN с CIDR-блокировкой; HTTP + SYN с лимитом;
HTTP + UDP с CIDR-блокировкой; HTTP + UDP с лимитом. Во всех XDP-прогонах
легитимный клиент 192.0.2.2 явно разрешён. Нагрузка приходит от 192.0.2.3.
CIDR-сценарии запрещают этот source IP. Лимиты: 10 000 PPS и 1 000 SYN/s
на source IP; окна фиксированы по монотонным секундам. TCP RST от синтетического
клиента подавляется в его namespace, чтобы SYN создавали нагрузку на TCP backlog.
UDP идёт на защищаемый порт без UDP listener; без XDP его обрабатывает стек Linux.

PPS задаётся 50 000, но отчёт содержит **фактически отправленный** поток. Все
компоненты делят CPU runner, поэтому поток может не достигать целевого PPS;
это нужно учитывать при сравнении пар. Виртуальные native/generic не дают оценки
производительности драйвера физической сетевой карты. Три коротких повторения
не являются статистическим доверительным интервалом или production sizing.

Для каждого прогона сохраняются HTTP RPS, p50/p95/p99, ошибки и status codes,
фактический PPS, число успешных access-записей после flush, CPU FESS, общий busy
CPU и softirq CPU, TCP ListenDrops/Syncookies и дельта XDP counters. Интервал
счётчиков включает завершение HTTP-запросов и генератора после окончания нагрузки;
они читаются до flush журнала. `successful_rps_including_drain` учитывает также
время flush/COUNT. CPU хоста включает все процессы runner; это не отдельная оценка
стоимости сетевого стека. Результаты являются артефактами workflow.
