# Нагрузочные проверки FESS

`native-2026-10-20.json` — первичный локальный прогон FESS 2.0.0 на Apple M4,
24 GiB RAM. В `native-sustained-2026-10-20.json` отдельно сохранены
30-секундные прогоны проксирования при 16 клиентах. Генератор, upstream, WAF, PostgreSQL и ClamAV работали на одном
компьютере по loopback. Фоновые приложения и системный антивирус оставались
включены. Эти цифры не являются гарантией производительности Linux-сервера.

Сценарии: прямой upstream, GET через WAF с одной политикой и журналированием,
блокировка WAF с записью события, POST 1 KiB с антивирусом. Для каждого сценария
использованы 1/16/64 параллельных клиента, прогрев 1 секунда и измерение 5 секунд.
Сохраняются RPS, p50/p95/p99, максимальная задержка, статусы и транспортные ошибки.
Модель closed-loop: каждый клиент отправляет следующий запрос после ответа;
это не измерение задержек при фиксированном внешнем потоке и не длительный soak.

ClamAV использовал минимальную тестовую базу сигнатур. Результат сценария
`upload-ClamAV-test-db` характеризует протокол и интеграцию, но не стоимость
проверки с полной production-базой и реальными архивами/документами.
SQLite использует WAL и стандартную надёжность записи; PostgreSQL — локальный
PostgreSQL 16 со стандартной конфигурацией. Логи записываются синхронно в БД,
stdout/stderr направлены в локальный файл. Базы для сравнения были свежими.

Первый прогон `initial-connection-churn-2026-10-20.json` обнаружил исчерпание
исходящих портов при стандартном upstream idle pool Go (2 соединения на хост).
В FESS увеличен пул keep-alive (256 idle / до 512 активных на upstream), после
чего основная серия повторена. Неудачный прогон хранится отдельно и не используется
как оценка текущей пропускной способности.

## Повторение

```sh
go build -o dist/fess-load ./cmd/fess-load
# Терминал 1: тестовый upstream
./dist/fess-load -serve 127.0.0.1:18080
```

Запустите отдельный FESS. В панели создайте сайт `app.test`, upstream
`http://127.0.0.1:18080`, политику блокировки с правилом `path_prefix=/blocked`.
На время проверки ёмкости отключите rate limit и защиту от ботов в этой тестовой
установке. Журналирование оставьте включённым.

```sh
./dist/fess-load -url http://127.0.0.1:18080/pass -concurrency 16 -duration 30s
./dist/fess-load -url http://127.0.0.1:8080/pass -host app.test -concurrency 16 -duration 30s
./dist/fess-load -url http://127.0.0.1:8080/blocked -host app.test -concurrency 16 -duration 30s
./dist/fess-load -url http://127.0.0.1:8080/upload -host app.test -method POST -body-bytes 1024 -concurrency 16 -duration 30s
```

Повторите для разных уровней параллельности и движков БД. Генератор выводит JSON;
для обычного проксирования ожидается 200, для блокировок — 403. Сам по себе 403 не
является ошибкой нагрузки. Транспортные ошибки приводят к ненулевому коду выхода.
Чтобы оценить production, используйте отдельный хост генератора, репрезентативные
политики/тела, полную базу ClamAV, TLS и длительный прогон с контролем размера БД,
CPU/RAM, очередей и потерянных записей журналов.
