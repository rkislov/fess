WAF и reverse proxy с веб-панелью, политиками без перезапуска, TLS/ACME,
антивирусом, защитой от ботов, IOC, журналами, LDAP/JWT и экспортом SIEM.

**Один Go-бинарник `fess`** содержит шлюз, API и собранную панель Nuxt.
SQLite используется по умолчанию; PostgreSQL подключается для больших установок.
ClamAV и freshclam устанавливаются пакетным менеджером ОС. Node.js и Go на
целевом сервере не нужны. Redis, Nginx и контейнерная инфраструктура не требуются.

## Установка на Linux

Скачайте установщик и запустите его на сервере. Нужны Python 3.8 или новее и `curl`. Команда одинакова для установки и обновления:

```sh
curl --retry 3 -fsSLo install-linux.py https://raw.githubusercontent.com/rkislov/fess/main/scripts/install-linux.py && python3 install-linux.py
```

Установщик определяет архитектуру пользовательской среды, скачивает `fess` и `fess-xdp` из [GitHub Releases](https://github.com/rkislov/fess/releases) и сверяет SHA-256. По умолчанию выбирается последний релиз. Для определённой версии выполните, например, `python3 install-linux.py 2.2.8`.

**Системная установка.** На Debian, Ubuntu и их производных с systemd установщик использует APT и DEB. На Fedora и системах семейства RHEL — DNF/YUM и RPM. Репозитории ОС должны предоставлять зависимости ClamAV (для RHEL может потребоваться EPEL). Перед первым запуском задайте свой `FESS_ADMIN_PASSWORD` в `/etc/fess/fess.env` и запустите службу:

```sh
sudoedit /etc/fess/fess.env
sudo systemctl start fess
```

**Переносимая установка.** На остальных дистрибутивах, включая Alpine, Arch, openSUSE, ALT и системы без systemd, установщик размещает статические бинарники в `~/.local/share/fess`. Этот вариант можно выбрать явно через `--portable` или `--prefix /путь/к/fess`. Для первого запуска задайте пароль в файле настроек, затем запустите WAF:

```sh
vi ~/.local/share/fess/etc/fess.env
~/.local/share/fess/current/start-fess
```

Переносимый WAF по умолчанию слушает веб-порты 8080 и 8443. Для автозапуска добавьте указанную команду в менеджер служб своего дистрибутива. ClamAV для переносимой установки ставится отдельно, его сокет задаётся в панели. Для XDP нужны поддержка BPF в ядре и права на сетевой интерфейс. На системе без systemd запускайте `fess-xdp --config /путь/xdp.json` из установки, принадлежащей администратору. Управление XDP из веб-панели использует системную службу контроллера.

**Архитектуры.** Начиная с 2.2.8 публикуются Linux-бинарники для x86 (32 и 64 бита), ARM (32 и 64 бита), RISC-V 64, LoongArch64, IBM Z, PowerPC64 и MIPS (32 и 64 бита). Для PowerPC64 и MIPS учитывается порядок байтов. Если в релизе нет готового архива для архитектуры, установщик собирает оба бинарника из проверенного архива исходников с готовой веб-панелью. Нужны нативный Go версии из `go.mod`, поддержка процессора компилятором и доступ к Go-модулям. Сборку можно выбрать явно через `--source`.

**Вход в панель.** Проверьте на сервере `curl -fsS http://127.0.0.1:8082/healthz` — ответ `ok` означает, что FESS запустился. На своём компьютере откройте SSH-туннель:

```sh
ssh -N -L 8082:127.0.0.1:8082 user@server
```

Подставьте пользователя и адрес сервера. Если порт SSH отличается от 22, добавьте `-p НОМЕР_ПОРТА` перед `user@server`. Оставьте соединение открытым и войдите как `admin` с заданным паролем на [http://127.0.0.1:8082](http://127.0.0.1:8082).

## Обновление на Linux

1. Сохраните конфигурацию и резервную копию базы по [инструкции администратора](docs/admin-guide.md#данные-и-резервное-копирование).
2. Повторите команду установки. Если выбирали `--prefix`, укажите прежний каталог. При переносимом обновлении установщик переключает оба бинарника вместе, сохраняя `etc/` и `data/`.
3. Для пакетной установки проверьте `systemctl status fess` и `fess version`. Если останавливали FESS для копирования базы, запустите его. При переносимой установке перезапустите процесс через свой менеджер служб и проверьте `~/.local/share/fess/current/fess version`.

## Запуск бинарника

```sh
./fess --data-dir ./data --admin 127.0.0.1:8082 --http :8080 --https ''
./fess version
./fess --help
```

Для антивируса нужен доступный системный `clamd`; путь к Unix-сокету задаётся в
панели. В небольших установках никаких других служб хранения данных не нужно.
Настройки, учётные записи и журналы сохраняются в `data/fess.db`. Счётчики rate
limit и временные оценки ботов хранятся в памяти и сбрасываются при перезапуске.
Один каталог данных и один SQLite-файл обслуживает один процесс FESS.

`FESS_CONFIG=/path/to/fess.env` загружает файл `KEY=value` без выполнения shell.
Переменные окружения имеют приоритет над файлом, флаги — над окружением.
Для systemd файл `/etc/fess/fess.env` загружается самой службой.

Основные параметры:

- `FESS_DATA_DIR`: каталог данных, по умолчанию `./data`.
- `FESS_DB`: `sqlite` или `postgres`.
- `FESS_DATABASE_URL`: путь SQLite либо DSN PostgreSQL.
- `FESS_ADMIN_ADDR`: адрес панели/API, по умолчанию `127.0.0.1:8082`.
- `WAF_LISTEN_ADDR`, `WAF_TLS_LISTEN_ADDR`: порты шлюза.
- `WAF_TRUSTED_PROXIES`: CIDR непосредственных доверенных прокси перед FESS.
- `FENCE_AI_*`: настройки внешней модели; их также можно задать в панели.

## Пакетное журналирование

По умолчанию `FESS_LOG_MODE=batch`: очередь до 8192 записей, пакеты до 256 строк,
сброс каждые 20 мс. SQLite использует подготовленный INSERT в одной транзакции,
PostgreSQL — многострочные INSERT. Заполнение очереди создаёт backpressure;
ошибки записи сохраняют пакет для повторной попытки. Время события фиксируется
до постановки в очередь. Чтение журналов/агрегатов через API дожидается барьера
записи, а штатная остановка сбрасывает хвост очереди.

При аварии процесса/хоста ещё не записанный хвост может потеряться. Для требования
«commit до ответа» задайте `FESS_LOG_MODE=sync`. Зависание/переполнение очереди при
ошибке БД может задерживать запросы; ошибки постановки/записи видны в журнале и
метриках `fence_log_*`. При невозможности сбросить очередь за срок остановки
процесс завершится с ошибкой и сообщит число незаписанных записей. Повторная
попытка после неопределённого результата COMMIT при сетевом сбое может дублировать
записи; exactly-once для событий не обещается.

## Необязательная защита XDP

Отдельный пакет `fess-xdp` добавляет CIDR-фильтрацию IPv4/IPv6 и лимиты пакетов/SYN
для выбранных TCP/UDP-портов на Linux 5.15+, общие бюджеты, ICMP Ping Flood,
проверки некорректных пакетов и временные баны WAF. В **Настройки → XDP** администратор
может выбрать интерфейс, сохранить параметры, запустить и остановить фильтр.
Установка запускает локальный контроллер; сам фильтр включается явно;
привилегии основного процесса FESS не меняются. [Установка и ограничения](docs/xdp.md).

## Перенос SQLite → PostgreSQL

Создайте **пустую** БД PostgreSQL. Сохраните резервную копию каталога данных и
остановите FESS на время переноса. Используйте тот же каталог данных: он содержит
JWT-секрет и GeoIP, которые не переносятся в SQL.

```sh
sudo systemctl stop fess
sudo -u fess env FESS_MIGRATE_TARGET='postgres://user:password@db:5432/fess?sslmode=verify-full' \
  /usr/bin/fess migrate --data-dir /var/lib/fess
```

Команда переносит таблицы в порядке зависимостей, сохраняет идентификаторы,
сверяет значения и количество строк, восстанавливает последовательности ID.
Данные PostgreSQL записываются в одной транзакции. При ошибке копирования данные
откатываются, но созданная схема остаётся — для повторного запуска используйте
пустую БД/схему. Исходная SQLite сохраняется.

Затем измените `/etc/fess/fess.env`:

```ini
FESS_DB=postgres
FESS_DATABASE_URL=postgres://user:password@db:5432/fess?sslmode=verify-full
```

```sh
sudo systemctl start fess
```

До начала новых записей можно вернуться к SQLite изменением конфигурации.
После начала записи в PostgreSQL старая SQLite уже не содержит новых данных.
PostgreSQL увеличивает возможности хранения; координация нескольких активных
процессов FESS в этом выпуске не реализована.

## Сборка и проверки

Требуются Go 1.26.9+ и Node.js 22+ только на машине сборки.

```sh
scripts/build.sh
./dist/fess --http :8080 --https ''
go test ./...
go test -race ./...
```

Сборка сначала генерирует статическую панель, затем включает её через `go:embed`.
Для проверки PostgreSQL и переноса данных задайте DSN тестовой БД:

```sh
FESS_TEST_POSTGRES='postgres://user:password@127.0.0.1:5432/test?sslmode=disable' go test ./integration
```

Тесты создают и удаляют собственные схемы; пользователю нужны соответствующие
права. Выпуск бинарников и deb/rpm: `FESS_VERSION=2.1.0 scripts/release.sh`; файлы появятся в `dist/releases/2.1.0/`.

## Исходники

- `cmd/fess`: единый запуск, конфигурация и команда переноса БД.
- `internal/api`, `internal/gateway`: управление и обработка трафика.
- `internal/runtimebus`: внутренние уведомления и счётчики с TTL.
- `internal/logbatch`: ограниченная очередь и пакетная запись событий.
- `cmd/fess-xdp`, `internal/xdpguard`: необязательный Linux XDP-фильтр.
- `db`: PostgreSQL-миграции, отдельные SQLite-миграции, адаптация SQL и перенос.
- `pkg`: WAF, маршрутизация, TLS, антивирус и другие компоненты.
- `ui`: панель; `packaging`: системные службы и пакеты.

### FESS завершает TLS за TCP-разделителем

FESS может быть единственным HTTP reverse proxy: порт 80 принимает HTTP-01 ACME и перенаправляет известные TLS-сайты на HTTPS; TLS завершается самим FESS. Сертификаты и ACME-аккаунт хранятся в БД и доступны в разделе «УЦ». Для ACME укажите email, существующий аккаунт либо создайте новый после согласия с условиями CA, привяжите сертификаты к сайтам и включите автоматическое продление.

Если Nginx разделяет HTTPS и VPN на внешнем 443, оставьте в нём только `stream`/SNI-маршрутизацию и `proxy_protocol on`. TLS listener FESS должен быть доступен только доверенным отправителям PROXY protocol, например:

```ini
WAF_LISTEN_ADDR=:80
WAF_TLS_LISTEN_ADDR=127.0.0.1:8443
WAF_TLS_PROXY_PROTOCOL_TRUSTED_CIDRS=127.0.0.1/32
WAF_TRUSTED_PROXIES=
WAF_HTTP_REDIRECT_HTTPS=true
# Необязательное перенаправление HTTP с другого имени:
# WAF_HTTP_CANONICAL_HOSTS=example.com=www.example.com
```

PROXY protocol v1/v2 принимается перед TLS и обязателен для указанного listener. Недоверенные TCP-отправители отклоняются. При передаче реального IP через PROXY protocol оставьте `WAF_TRUSTED_PROXIES` пустым, чтобы клиентские X-Forwarded-* не подменяли адреса и схему. Для прямого TLS без TCP-прокси не задавайте `WAF_TLS_PROXY_PROTOCOL_TRUSTED_CIDRS`.

Для VPN-подписок и других маршрутов, где backend ожидает полный исходный URL-путь, включите «Сохранять префикс пути» в настройках пути сайта. По умолчанию префикс удаляется, как в предыдущих версиях.
